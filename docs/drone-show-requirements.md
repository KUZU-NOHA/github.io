## 1. プロジェクト概要

### 1.1 背景と目的

多数のドローンを編隊飛行させ、機体に搭載した LED の発光パターンと飛行軌道を同期させることで、夜空に立体的な映像・文字・アニメーションを描く「ドローンショー」を実施したい。本書は、それを実現するための**ソフトウェアプログラム**（振り付け設計〜シミュレーション〜実機への指令配信〜監視・緊急停止まで）の要件を定義する。

**実機（本物のドローン群）を実際に空に飛ばして本番を実施すること**を前提とする。したがって、映像制作にとどまらず、機体・測位・通信・法規制・安全設計を含めた「実運用可能なシステム」としての要件を対象とする。

### 1.2 ゴール

**「振り付けを設計し、シミュレーションで安全性を検証したうえで、実機ドローン群を自律飛行させてショーを実施できる状態にする」**

### 1.3 対象規模（初期スコープ）

ドローンショーは機数が増えるほど難易度・費用・法規制対応が非線形に増大する。初期スコープは以下とする。

| 項目 | 初期目標 |
|---|---|
| 機数 | 20〜50機（小規模ショー） |
| 飛行形態 | 目視内飛行（VLOS）、日没後の夜間飛行 |
| 実施場所 | 十分な広さの私有地・許可取得済み屋外会場（観客との距離を確保できる場所） |
| 表現 | 静止フォーメーション＋緩やかな移動アニメーション、LED発色パターン |

> **設計上の指針**: いきなり数百機規模の商用ショー（Intel Shooting Star や EHang クラス）を目指さず、まず「10〜50機で安全に飛ばし切れる」設計を完成させる。機数のスケールアップは、測位精度・通信帯域・法規制対応のいずれもボトルネックになるため、後続フェーズで段階的に評価する。

### 1.4 スコープ外（初期リリース）

- 数百〜数千機規模の商用フルスケールショー
- 有人地帯上空でのレベル4飛行（BVLOS・第三者上空、第一種機体認証相当）
- 花火・レーザー等、ドローン以外の演出要素との統合演出
- 独自の機体設計・製造（既製の開発者向けプラットフォームを利用する前提）

## 2. 実現可否の技術的結論

### 結論: **実現可能**。ただし「ソフトウェア開発」と「実機での本番実施」は難易度が別次元であり、後者は法規制・保険・現地オペレーションへの依存が大きい。

本プロジェクトが開発するのは、以下の4段階を担う**ソフトウェアスタック**である。実際に機体を空に飛ばす行為そのものは、機体・電波・気象・法規制という4つの外部要因に強く制約される。

```
① 振り付け設計（3Dアニメーション）
       ↓
② シミュレーション・衝突検証（安全性の事前確認）
       ↓
③ ミッション生成・配信（機体ごとの軌道ファイルをアップロード）
       ↓
④ 本番監視・緊急停止（離陸〜着陸までの地上局オペレーション）
```

### 2.1 制約1 — RTK測位なしでは編隊は組めない

一般的なスマホ・カーナビ用GPSの測位誤差は数m〜十数mあり、複数機を数m間隔で編隊飛行させると誤差だけで機体同士が接触しうる。ドローンショーは**RTK（Real Time Kinematic）測位**または高品質GNSSモジュール（例: u-blox F9P/M8P）による**十〜数十cm精度**の測位が前提となる。

| 方式 | 精度 | 備考 |
|---|---|---|
| 単独GPS | 数m〜十数m | ショー用途には不適 |
| RTK（固定局＋移動局） | 1〜10cm | 会場に固定基地局（ベースステーション）の設置が必須 |
| 高品質GNSS単独（RTKなし） | 1〜3m | 機体間隔を2〜3m以上確保すれば小規模ショーは成立しうる |

初期スコープ（20〜50機、機体間隔2m以上）では「高品質GNSS単独＋広めの間隔」でも成立させられるが、密な編隊表現をしたい場合はRTK基地局の導入が事実上必須になる。

### 2.2 制約2 — 「リアルタイム操縦」ではなく「事前計算・自律飛行」が正しいアーキテクチャ

多機を人間が個別に操縦することは不可能であり、また通信帯域の観点からも「地上から常時、各機に制御コマンドを送り続ける」方式は機数が増えるほど破綻する。実運用されているドローンショーは例外なく以下の方式を採る。

1. 振り付けソフトウェア上で**各機の軌道（時刻×位置×発光色）を事前に計算**する
2. 飛行前に、各機体へ**自分専用の軌道ファイルを無線でアップロード**する
3. 離陸後は各機体が**GPS時刻同期を基準に、あらかじめ持っているデータを自律的に再生**する（＝地上からのリアルタイム制御コマンドに依存しない）
4. 地上局は**監視とステータス受信、および緊急停止（Kill/RTH）コマンドの一斉送信のみ**を担う

これにより、通信は「大容量の事前アップロード（飛行前・低頻度）」と「軽量なテレメトリ（飛行中・低帯域）」に分離でき、機数を増やしても通信要件が線形に爆発しない。

### 2.3 制約3 — 日本国内での実機実施には航空法上の許可が必須

100g以上の無人航空機は航空法の規制対象であり、ドローンショーは典型的に以下の「特定飛行」に該当するため、**国土交通省への許可・承認申請（DIPS2.0）**が必須になる。

- 夜間飛行（日没後の実施が通常のため）
- 催し場所（祭礼、縁日、展示会等の多数の者が集まる催しが行われている場所）の上空における飛行
- 機体間隔が近い場合の目視外・自動飛行に関する追加確認

詳細は第7章を参照。**これはソフトウェア開発の範囲外だが、本番実施の前提条件として必ず並行して進める必要がある。**

### 2.4 制約4 — 電波法：数十〜数百機が同時通信する際の周波数輻輳

多数の機体が同時にテレメトリを送信すると、使用する周波数帯（2.4GHz帯や920MHz帯の特定小電力無線）の帯域を圧迫し、通信の取りこぼしが安全上のリスクになる。対策の方向性は以下。

- 飛行中の通信は「低頻度のステータス送信」と「緊急停止コマンドの受信」に限定し、常時の位置制御通信を行わない（2.2節のアーキテクチャに従う）
- メッシュネットワークまたは時分割（TDMA的）な通信方式を採用し、輻輳を回避する
- 使用する無線機器は電波法上の**技術基準適合証明（技適）**を取得済みのものを使用する

## 3. システム構成

### 3.1 全体構成

```
┌───────────────────────────── 地上局（PC / タブレット） ─────────────────────────────┐
│                                                                                        │
│  ┌──────────────┐   ┌──────────────┐   ┌──────────────┐   ┌──────────────────┐    │
│  │ 振り付け設計   │──▶│ シミュレーター │──▶│ ミッション生成 │──▶│ 地上局(GCS)ソフト │    │
│  │ ・3Dアニメ    │   │ ・衝突検証    │   │ ・軌道分割    │   │ ・機体監視        │    │
│  │ ・隊列/経路   │   │ ・時間同期検証 │   │ ・機体別割当  │   │ ・一斉緊急停止    │    │
│  │ ・発光パターン │   │ ・電池残量試算 │   │ ・LEDタイムライン│  │ ・リハーサル記録  │    │
│  └──────────────┘   └──────────────┘   └──────┬───────┘   └─────────┬──────────┘    │
└───────────────────────────────────────────────┼─────────────────────┼───────────────┘
                                                   │ 事前アップロード（Wi-Fi/無線）        │ テレメトリ／Kill信号
                                                   ▼                                     ▼
                                   ┌──────────────────────────────────────────────────┐
                                   │              機体側（機数分。20〜50機）              │
                                   │  フライトコントローラ（ArduPilot/PX4 等）             │
                                   │  ・GPS/RTK受信機（高精度測位）                        │
                                   │  ・GPS時刻同期（フリート全体の同期基準）               │
                                   │  ・軌道リプレイ（自律飛行）                            │
                                   │  ・LEDコントローラ（発光パターン再生）                  │
                                   │  ・フェイルセーフ（バッテリ低下/リンク断→自動RTH/着陸）│
                                   └──────────────────────────────────────────────────┘
                                                   ▲
                                   ┌──────────────────────────────┐
                                   │ RTK基地局（会場に固定設置）      │
                                   └──────────────────────────────┘
```

サーバーは会場に必要（クラウド常時接続を前提にできないため、**現地でオフライン完結**する構成とする）。

### 3.2 技術スタック

| レイヤ | 採用技術（案） | 選定理由 |
|---|---|---|
| 振り付け設計 | Blender ＋ [Skybrush Studio](https://skybrush.io/)（OSSアドオン） | 3Dアニメーションから直接ドローン軌道を生成できる実績あるOSSパイプライン。ゼロから独自ツールを作るより検証コストが低い |
| シミュレーション・衝突検証 | Skybrush Studio 内蔵の衝突チェッカー ＋ 自作の追加検証スクリプト（Python） | 「同一時刻に2機がN m以内に接近しないか」を全ペア・全時刻で検証する必要があり、独自の安全マージン基準を追加する |
| ミッション生成・地上局 | [Skybrush Server](https://skybrush.io/) ＋ Skybrush Live（Web UI） | ArduPilot 機体への軌道アップロード・GPS時刻同期・一斉離着陸・緊急停止までを担う、実機運用実績のあるOSS |
| フライトコントローラ | ArduPilot（Copter, Guided/Auto モード） | MAVLink 経由で軌道追従が可能。Skybrush との連携実績が豊富 |
| 測位 | u-blox F9P（RTK）または M8P | ドローンショー用途で広く使われるモジュール |
| 発光 | WS2812B系アドレサブルRGB LED ＋ 機体側コントローラ | フライトコントローラのタイムラインと同期して発色パターンを再生 |

> **方針**: 独自にフライトスタックを一から実装するのは安全上のリスクが大きい（衝突検証・フェイルセーフの再発明はバグの温床になる）。実機運用実績のある OSS（Skybrush ＋ ArduPilot）を土台にし、本プロジェクト独自の付加価値は「振り付けデザインの使いやすさ」「日本国内運用に合わせた安全マージン・チェックリストの実装」に置く。


## 4. 機体・ハードウェア要件

### 4.1 ドローン本体

| 項目 | 要件 |
|---|---|
| プラットフォーム | ArduPilot 対応のショー用ドローン（開発者向けキットまたは市販ショー機体） |
| 重量 | 250g前後を目安とする（航空法上、100g以上は規制対象。軽量化は墜落時のリスク低減にも直結） |
| フライトコントローラ | ArduPilot 対応FC（Pixhawk系等） |
| GPS/RTK受信機 | u-blox F9P（RTK）または同等品 |
| LED | アドレサブルRGB（機体からの視認性を考慮し高輝度タイプ） |
| バッテリ | ショー全体（離陸〜演目〜着陸）を安全マージン込みで賄える容量。低電圧時の自動RTH/着陸を必須実装 |
| 通信 | 2.4GHz または 920MHz 帯（技適取得済み機器） |

### 4.2 地上系

| 項目 | 要件 |
|---|---|
| RTK基地局 | 会場に固定設置し、全機体に補正情報を配信 |
| 地上局PC | Skybrush Server 等を稼働させるノートPC（現地オフライン運用が前提） |
| GPS時刻同期基準 | フリート全体の飛行・発光タイミングをそろえる基準（GPS由来の時刻を各機体が共有） |
| 予備機体 | 本番当日の不具合個体を即座に差し替えられる予備を確保（推奨: 稼働機数の10〜20%） |

## 5. 機能要件

### 5.1 振り付け設計

| ID | 機能 | 優先度 |
|---|---|---|
| F-101 | 3Dアニメーションから機体別の軌道（時刻×XYZ座標）を生成 | 高 |
| F-102 | 発光パターン（色・輝度・タイミング）を軌道と同一タイムラインで設計 | 高 |
| F-103 | 離陸位置（グリッド配置）から各機体への役割自動割当 | 高 |
| F-104 | フォーメーション間の遷移経路の自動生成（直線・曲線の補間） | 中 |

### 5.2 シミュレーション・安全検証

| ID | 機能 | 優先度 |
|---|---|---|
| F-201 | 全機体ペア・全時刻での最小距離チェック（安全マージン未満を検出） | 高 |
| F-202 | 上昇・下降速度、最大速度・加速度が機体スペック内に収まっているかの検証 | 高 |
| F-203 | 軌道長・飛行時間からのバッテリ消費試算、残量不足の警告 | 高 |
| F-204 | 3Dビューでのプレビュー再生（本番前の目視確認用） | 高 |
| F-205 | 風速・突風を仮定した位置誤差マージンのシミュレーション | 中 |

> **F-201 が最重要である理由**: 実機での衝突は機体損壊だけでなく、地上の人・観客への落下物リスクに直結する。シミュレーション段階での検証を経ないミッションは、本番アップロードの対象にしてはならない（後述 F-303 でシステム的に強制する）。

### 5.3 ミッション生成・配信

| ID | 機能 | 優先度 |
|---|---|---|
| F-301 | 機体別ミッションファイルの生成（軌道＋発光＋機体IDの紐付け） | 高 |
| F-302 | 現地での機体IDとミッションファイルの対応付け（誤配線防止） | 高 |
| F-303 | 衝突検証（F-201）に合格していないミッションのアップロードをブロック | 高 |
| F-304 | 離陸前チェックリストの自動化（GPS Fix数・RTK Fix状態・電池電圧・機体位置オフセット） | 高 |

### 5.4 本番監視・制御

| ID | 機能 | 優先度 |
|---|---|---|
| F-401 | 全機体のリアルタイムステータス表示（位置・電池・GPS状態） | 高 |
| F-402 | 一斉離陸トリガー（GPS時刻同期による同時発進） | 高 |
| F-403 | **緊急停止（一斉RTH／その場ホバリング後の自動着陸）を1操作で発動** | 高 |
| F-404 | 個別機体の異常検知時の自動除外（該当機のみRTHし、他機は演目継続） | 中 |
| F-405 | リハーサル飛行の記録・本番との差分比較 | 中 |

## 6. 非機能要件

### 6.1 性能

| 項目 | 要件 |
|---|---|
| 機体間の時刻同期精度 | 数十ミリ秒以内（発光・隊列のズレを視認できないレベル） |
| 測位精度 | RTK使用時 10cm以内、非RTK時は機体間隔を精度に応じて自動拡大 |
| 緊急停止コマンドの到達時間 | 発動から全機体への到達まで1秒以内を目標 |

### 6.2 安全性（最重要）

| ID | 要件 |
|---|---|
| SA-01 | 通信リンク断時、機体は自動的にRTH（帰還）または安全な自動着陸を行う（フェイルセーフ必須実装） |
| SA-02 | バッテリ残量が閾値を下回った機体は演目を中断し自動着陸する |
| SA-03 | 観客エリアと飛行エリアの間に、地上局から独立した物理バリケード（立入制限区画）を設ける（ソフトウェアだけに頼らない） |
| SA-04 | 風速が安全基準（機体スペックに基づく上限値、目安として5m/s前後）を超えた場合は自動的にフライト不可とする |
| SA-05 | 衝突検証未合格のミッションは物理的にアップロードできない（F-303） |
| SA-06 | 緊急停止は地上局の単一障害点に依存しない（操作者が複数、または独立した無線Kill機構を用意） |

### 6.3 信頼性・運用性

| ID | 要件 |
|---|---|
| RE-01 | 現地はインターネット接続を前提とせず、ローカルネットワークのみで完結する |
| RE-02 | 本番当日は必ずリハーサル（同一ミッションでの試験飛行）を実施してから観客を入れる |
| RE-03 | 個体不良に備え、予備機体とホットスワップ手順を用意する |

## 7. 法規制・許認可要件

> **注記**: 本章は調査時点の一般的な制度理解に基づく整理であり、法的助言ではない。実施前には必ず[国土交通省の無人航空機ページ](https://www.mlit.go.jp/koku/koku_fr10_000041.html)で最新の制度・様式を確認し、必要に応じて行政書士等の専門家に相談すること。

| ID | 要件 | 概要 |
|---|---|---|
| L-01 | 機体登録 | 100g以上の無人航空機は国土交通省への機体登録（登録記号の表示）が必須 |
| L-02 | 操縦者技能 | 無人航空機操縦者技能証明（国家資格）の取得、または同等の講習修了が望ましい |
| L-03 | 飛行許可・承認申請（DIPS2.0） | 夜間飛行・催し場所上空飛行に該当するため、国土交通省への許可・承認申請が必須。実施予定日の**十分前**（一般に数週間〜1か月以上を目安）に申請すること |
| L-04 | 催し場所上空飛行の追加基準 | 立入り制限区画の設置、実施前のリハーサル、気象条件（風速等）の確認など、催し場所上空飛行に関する追加の安全基準への適合が求められる |
| L-05 | 電波法 | 使用する無線機器は技術基準適合証明（技適マーク）取得済みのものに限定する |
| L-06 | 賠償責任保険 | 対人・対物賠償に備えた保険加入（多数機を同時運用するため、機体保険とは別に十分な補償額のイベント保険を推奨） |
| L-07 | 会場・自治体との調整 | 消防・警察への事前相談、近隣への周知（騒音・光害への配慮）が実務上必要になることが多い |

## 8. リスクと対策

| # | リスク | 影響度 | 対策 |
|---|---|---|---|
| R-01 | 機体同士の空中衝突 | 極高 | シミュレーション段階での全ペア衝突検証を必須化（F-201, F-303）。安全マージンを機体スペックより保守的に設定 |
| R-02 | 観客・第三者への機体落下 | 極高 | 立入制限区画の物理設置（SA-03）、フェイルセーフ必須実装（SA-01/02）、催し場所上空飛行の追加基準遵守（L-04） |
| R-03 | GPS/RTK測位の一時的な劣化（マルチパス、衛星減少） | 高 | 測位精度が閾値を下回った機体を自動的にRTH。RTK基地局の設置場所選定（開けた場所）を事前検証 |
| R-04 | 通信輻輳による緊急停止コマンドの遅延 | 高 | 飛行中通信を低帯域化する設計（2.2節）。緊急停止は独立系統も検討（SA-06） |
| R-05 | 強風・悪天候 | 高 | 風速閾値によるフライト可否判定を自動化（SA-04）。荒天時の順延・中止基準を事前に明文化 |
| R-06 | 法規制対応の遅延（許可が本番に間に合わない） | 高 | L-03の申請を実施日の1か月以上前から着手。行政書士等への相談も検討 |
| R-07 | 個体のバッテリ・機体不良 | 中 | 離陸前チェックリスト（F-304）と予備機体（4.2節）でカバー |
| R-08 | 現地ネットワーク・電源トラブル | 中 | オフライン完結設計（RE-01）、発電機・UPS等のバックアップ電源を用意 |

## 9. 開発フェーズ計画

| Phase | 内容 | 完了条件 |
|---|---|---|
| Phase 0<br>技術検証 | シミュレータ環境の構築、ArduPilot機体1〜2機での基礎飛行・軌道追従テスト | 1機がPCから送った軌道どおりに屋外で飛行する |
| Phase 1<br>小規模編隊 | 5〜10機での同時離陸・編隊飛行・LED同期の実証（人のいない安全な場所で） | 複数機が衝突せず、意図した隊列・発光を再現する |
| Phase 2<br>安全機構の実装 | フェイルセーフ（SA-01〜06）、緊急停止、離陸前チェックリストの実装 | 意図的に通信を切断・電池を強制低下させても機体が安全に着陸する |
| Phase 3<br>法規制対応 | DIPS2.0申請、保険加入、会場調整（第7章） | 実施許可が取得できている |
| Phase 4<br>本番規模（20〜50機） | 目標機数でのリハーサル、観客を入れた本番実施 | 計画どおりのショーを安全に実施できる |
| Phase 5<br>スケールアップ検討 | 機数増加時のRTK基地局増設、通信方式の再評価 | — |

> 各Phaseは「安全に飛ばせる規模」を段階的に広げる構成。**Phase 2（安全機構）を飛ばして機数だけ増やすことは絶対に行わない。**

## 11. 本書の前提

以下はユーザーへの確認が取れていない項目である。確定した時点で該当章の見直しが必要。

| # | 前提として置いた内容 | 変更時に影響を受ける章 |
|---|---|---|
| 1 | 実施場所 = 日本国内、私有地または許可取得済み屋外会場。海外での実施の場合、法規制（第7章）は全面的に作り直しが必要 | 第7章 |
| 2 | 初期規模 = 20〜50機。既に機体を保有しているか、これから調達するかは未確認 | 第4章、第10章 |
| 3 | 技術基盤 = ゼロからの自社開発ではなく、Skybrush＋ArduPilotのようなOSS実績を土台にする方針。独自フライトスタックを強く希望する場合は難易度・開発期間が大幅に増加する | 第3章、第9章 |
| 4 | 操縦者 = 無人航空機操縦者技能証明を保有する担当者が確保できる前提（未取得の場合、講習受講がフェーズ0の前提条件になる） | 第7章、第9章、第10章 |
| 5 | 予算感 = 未確認。商用ドローンショー会社への委託という選択肢も含め、内製と委託のどちらを志向するかで以降の設計が大きく変わる | 全章 |

### 確認したい事項

- 実施予定日・場所（許可申請のリードタイム確保のため、できるだけ早期に確定したい）
- 目標機数と演出内容（イメージ画像・動画があれば参考にしたい）
- 内製（本プログラムを実際に開発・運用）か、既存の商用ドローンショー事業者への委託かの方向性
- 操縦者技能証明の保有状況
